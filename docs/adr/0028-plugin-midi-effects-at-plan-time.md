# 0028. Plugin MIDI effects run in their worker when the plan is compiled

- Status: Accepted; amends 0022 and 0025; amended by 0035 (live input)
- Date: 2026-10-10

## Context

Playback plays an immutable plan compiled ahead of time (ADR 0006), and built-in devices run when it is compiled
(ADR 0022). Plugins never run in Bluestone's process (ADR 0025), and there is no audio engine to drive them during
playback. Until now a plugin MIDI effect therefore passed events through unchanged at plan time, with a diagnostic,
so what it put out never reached hardware, racks, or other tracks. The epic requires that MIDI events generated by
plugins can be routed downstream.

## Decision

- **Plan compilation asks the device's own worker to run the plugin offline.** A `RenderEvents` control message
  (protocol version 2) carries the plugin identity, the state and parameter values the project stores, the
  device's automation as parameter changes at sample frames, the tempo map, and the events the device handles.
  The worker runs a fresh copy of the plugin over the timeline in blocks and replies with what it put out
  (`RenderedEvents`). Live instances are not touched.
- **The project is the input.** The render starts from the project's stored state and parameters, not from the
  live instance, so the same project compiles to the same plan.
- **Time travels as sample frames on the tempo map.** The n-th event the plugin puts out at a frame answers the n-th
  event sent at that frame and takes its exact tick, so ticks that share a frame (very high resolutions) come back
  apart; events at other frames are converted back through the tempo map. A note shorter than a frame is sent
  ending one frame after it starts, so the plugin always sees it start first. Note-on and note-off pairs become
  notes again. Output events take their place in the canonical order from the input they match, and keep that
  input's ID when they are the same kind of event; otherwise they get an ID derived from it.
- **Failure never fails the plan.** A worker that is gone, does not answer within the request timeout (it is then
  stopped, like any hung worker), or reports a plugin error leaves the events unchanged, and the plan says why. A
  request over the protocol's limits is not sent and is reported the same way.
- **Only MIDI effects are rendered.** Instruments and audio effects still need an audio engine. The renderer is a
  seam in `Bluestone.Signal` (`IOutOfProcessRenderer`); the chain runner calls it only for a device it says it can
  run, and only when the plan is compiled, never from a real-time path.
- **Recompiling.** The app compiles off the UI thread when a project has such a device, and compiles again when a
  plugin MIDI effect's status changes (it crashed, or it was restarted).

## Consequences

- A plugin MIDI effect's output is routed like a built-in device's: to external instruments, racks, other tracks,
  and through taps. Its automation applies from its own frame.
- Compiling a plan with plugin MIDI effects costs a round trip per device per compile, and up to the request
  timeout when a worker hangs.
- A render cannot model run-time interaction (a plugin that reacts to live input during playback); the plan holds
  what the plugin produces from the arrangement. Live notes still bypass plugin devices.
- Each render is independent, so a plugin's state does not carry across compiles, which is what a plan needs.
